# Automatic Tempo settlement

The hosted Sites Worker commits a match record, produces its deterministic result, signs the exact V6 EIP-712 settlement with the configured one-signer private key, submits the Tempo transaction from that funded signing account, verifies finalized receipt data, and updates the player's payment history. The bounded MPP relayer forwards exact reward and entry payments; it is a temporary custodial forwarding path. V6 is the live escrow and its on-chain timeout failsafe refunds a held entry and reopens an unsettled attempt. The player authorizes funding/entry, builds and watches; they never authorize a settlement transaction.

The live V6 deployment uses one settlement signing secret in the trusted Sites Worker secret binding; it must never be placed in frontend code, a plain environment variable, Git, D1 or a browser. The signer also needs funded pathUSD for Tempo transaction fees. Changes to this documentation or application code do not redeploy the immutable contract.

## Trust and payment rules

`settlement/protocol.mjs` canonicalizes the complete record and deterministic result. Its SHA-256 result commitment includes the engine release, both builds and rules, seed, chain, escrow, bounty/attempt identity, creator and challenger, deadline, entry, gross reward, fee and exact payout. The configured V6 signer signs the exact EIP-712 settlement domain and message for the deployed escrow, and the backend independently compares signed amounts with the contract's immutable bounty. V6 uses EIP-712 domain version `6`, held entries, and a finalized timeout-refund event.

The contracts fix recipients and amounts. The Sites signer submits only the exact settlement call; the MPP relayer can forward only the exact payer, recipient, reward or entry supplied by the verified payment route. Neither key can choose arbitrary calldata, recipients, amounts, or a V6 refund recipient. The backend keeps the signing and relayer bindings server-side; the browser and D1 contain no private key material.

The non-upgradeable V6 contract pays a winning challenger 97.5% of the gross reward, rounding the 2.5% fee down in base units. It holds the entry until settlement: a settled outcome pays it to the creator, while the on-chain timeout failsafe refunds it to the challenger and reopens an unsettled attempt. V6 timeout is a technical refund, not a player loss. The open bounty itself has no forced lifetime.

Existing V2 result rows are adopted only if the deterministic legacy hash can be reproduced from their stored data and recorded timestamp. Their already-issued message is preserved. Legacy signatures bind amounts via the immutable on-chain bounty identifier; new records additionally include amounts in their result hash. Unreproducible records and old synthetic technical-refund records are not signed automatically. Never reconstruct a missing build, timestamp or result by guessing.

## Optional legacy/future multi-signer topology

The following separate signer services describe an optional hardening deployment. They are not required by the active V6 one-signer Worker and are not implied to be deployed.

The planned multi-signer model gives each signer its own Worker, D1 decision journal, secret-manager key and RPC endpoint. The active V6 deployment uses one configured signer instead, so those independent checks are a future hardening path rather than a current quorum guarantee. Each signer can independently retrieve the immutable record, validate blueprints, rerun the pinned engine, recompute the exact payload, verify the finalized entry and on-chain terms, and verify its own on-chain authority. A signer records its decision before signing and refuses another commitment for the same escrow bounty/nonce. Database triggers forbid changes to committed match inputs and settlement message fields. D1 operators and release administrators remain trusted: database triggers do not protect against an administrator dropping the schema. Keep their privileges separate from signer key administrators and export audit logs to restricted retention storage.

| Service | State | Secrets Store bindings |
| --- | --- | --- |
| API/coordinator | Existing app D1; match records, jobs, leases, audit, pause | Per-service outgoing and incoming authentication keys; operator/scheduler/monitor authentication |
| Signer A | Independent D1 decision journal | Existing approved signer A key; A's two authentication keys |
| Signer B | Independent D1 decision journal | Existing approved signer B key; B's two authentication keys |
| Relay | Dedicated D1 audit plus one Durable Object | Separate relay key; relay's two authentication keys |
| Operator dashboard | Cloudflare Access identity | Operator-to-API authentication |
| Monitor | Independent D1 notification state and Analytics Engine | Monitor-to-API authentication; notification webhook |

Service bindings keep signer/relay endpoints off the public Internet. Every call additionally authenticates a HMAC over caller, audience, method, path, timestamp, nonce and canonical body. Requests expire after 30 seconds; persisted nonce constraints reject replays; each authenticated caller is limited to 120 calls/minute. Only an attempt identifier is accepted by signer and relay entrypoints. Public signatures and serialized signed transactions are broadcast artifacts, not secrets; journals may contain these, but never key/password material. Error responses/logs contain bounded codes, never raw provider exceptions or request bodies.

## Deployment

Use Node 22.21.1 or compatible newer Node and a current Cloudflare Wrangler release approved for your environment. Start with a staging Cloudflare account and controlled escrow/RPC fixtures; the shipped mainnet address is deliberately pinned. Testing another on-chain escrow requires a separately reviewed staging build with consistent domain/address pins. Do not send a test transaction from this checkout to mainnet merely to test deployment.

Before an engine stamp release, register a frozen evaluator and catalog for the current release and retain the current and audited legacy evaluators needed by unresolved or funded bounties. A stamp release does not archive the outgoing evaluator automatically: fail closed for new entries when an evaluator is unavailable, while retaining the evaluator required to settle existing commitments. This is a bounded registry, not an unlimited history guarantee.

1. Run `npm ci`, `npm test`, `npm run build:sites`, and `npm run build:settlement`. Keep the same engine stamp on all three verifiers. Engine upgrades require draining existing matches or retaining their old verifier release.


2. Copy `deploy/*.wrangler.jsonc` into environment-specific configurations and replace the resource identifiers. The files contain only public settings and secret **references**. Use the existing app D1 for `wm-api`; the active V6 signer secret and relay secret are protected Worker bindings. Separate signer A/B D1 databases and independent RPC endpoints apply only to the optional future multi-signer topology.
3. Back up app D1. Apply migrations `0000` through `0003` if absent, then `0005_automatic_settlement.sql`. **Do not rerun the historical `0004_reset_bounty_board.sql` reset on an existing production database.** Configure the API D1 `migrations_dir` to the application's migration directory only when its migration history is already correct; otherwise apply the new migration explicitly: `npx wrangler d1 execute wm-api --remote --file drizzle/0005_automatic_settlement.sql --config deploy/api.wrangler.jsonc`. Apply `settlement/service-schema.sql` once to each new signer, relay and monitor D1 using its own config. Preserve the relay Durable Object migration and storage on every release.
4. The key administrator must bind the one **existing approved** V6 signer secret through the protected Worker secret store or an approved secure import process. The immutable deployed escrow approves that public signer address; arbitrary replacement keys cannot settle it. If that authority is unavailable, preserve existing obligations and deploy a separately reviewed escrow. The two-signer import procedure is optional future deployment material.
5. Provision a distinct relay key in its own Secrets Store and fund its address with pathUSD for transaction fees. No player supplies this fee funding. Set the matching public `RELAY_ADDRESS`. Generate independent random authentication secrets in the secret manager and bind exactly the named per-service references in the configs. Do not use shell arguments, `.env`, source code, chat, logs or D1 to transport private keys. Binding `get()` is required; a plaintext string environment variable is rejected.
6. Deploy the active Worker/API and its scheduled handler with the reviewed Sites configuration, binding the one signer secret and relay secret through protected bindings. Optional signer A/B service bindings belong to a separately reviewed future multi-signer deployment. Preserve the existing audience and wallet sign-in origin.
7. Configure a Cloudflare Access application with MFA and a small operator allowlist for a separate operator hostname. Set its team domain, audience and allowed operator email addresses, then deploy `deploy/operator.wrangler.jsonc`. The dashboard validates Access JWT signatures itself and checks request origins for mutations. Never expose an unprotected operator route.
8. Configure an HTTPS notification webhook in Secrets Store, deploy `deploy/monitor.wrangler.jsonc`, and verify its Cron Trigger, structured health event, Analytics Engine dataset and notification delivery. Alerts cover stale coordinator heartbeat, overdue jobs, timeouts and API failure. Repeated alerts are limited to every 15 minutes, with immediate state-change/recovery notifications. Alert-delivery failures also fail the monitor invocation; enable Cloudflare Worker failure notifications for that Worker as the fallback channel.
9. Keep `WM_RESULT_SIGNING_READY=false` until the operator dashboard shows healthy signer addresses and relay, recent heartbeat, configured notification delivery and no unexplained legacy attempts. Migration 0005 starts globally paused. Use **Resume services** in the operator dashboard, then enable `WM_RESULT_SIGNING_READY=true` only after a healthy tick. New entry/funding checks require configured service bindings, fresh heartbeat and an unpaused database control. Losing readiness fails closed for new money.
10. Verify the player flow in a controlled environment: commit → verification → broadcast → finalized receipt → Paid/Loss settled/Draw settled, including the signer outage drill, RPC failure, process restart after broadcast and timeout. Reconcile test receipt fields and token movements independently before opening production. The automated tests use ephemeral keys and mocked RPCs; they are not a mainnet payout test or a contract security audit.

## Scheduling, retries and finality

The main Worker's scheduled handler drains due jobs; the Cron Trigger runs every minute. Jobs are inserted atomically with the immutable match record by a database trigger. A worker leases a job with a compare-and-swap update, persists accepted signatures, and retries with bounded backoff. Restarting between record creation and simulation is recoverable. Expired construction windows are automatically committed as losses while the contract signing window remains open. Capacity must leave enough time inside the contract deadline; monitor backlog and raise worker capacity before accepting more entries.

The relay uses a stable, independent Tempo nonce lane for each attempt and journals serialized transactions **before** broadcast. Lost responses rebroadcast identical bytes. Bounded fee increases preserve all settlement calldata, recipient, amount, nonce and expiry; every replacement hash remains in the relay journal. No unrelated match waits behind a dropped transaction's nonce. Set `MAX_RELAY_GAS` and `MAX_FEE_PER_GAS` for your fee budget; the supplied limit is a deployment setting, not a current gas-price estimate. Monitor/fund the relay fee balance outside player sessions.

Both coordinator and API verify a successful receipt, canonical receipt block hash, finalized block height, chain ID, exact escrow event, bounty/nonce, challenger, outcome, result hash, payout, fee and creator entry. A mined transaction alone never sets a completed payout. Timeouts keep reconciling previously submitted hashes, since a transaction submitted before the deadline can finalize afterward. Contract nonce/status enforcement prevents a second payout even if duplicate relays broadcast the same fully signed result.

## Operator controls and recovery

Open the Access-protected dashboard to pause/resume, request a recovery tick, retry a job, inspect metrics and read the append-only audit trail. No operator signature generation is part of normal settlement. The global database pause is checked before signing and broadcasting; `WM_EMERGENCY_PAUSE=true` is an additional per-service fail-safe. Read-only receipt reconciliation continues while paused. The existing contract cannot revoke signatures or halt a transaction already broadcast, so pausing cannot promise to stop those payments.

Do not delete decision journals, clear relay storage, change a match record or reset nonce history to retry a failed payment. Repair the failed RPC/secret binding, restore the signer, replenish the relay fee balance or adjust its approved fee ceiling, then request Retry. A deadline cannot be extended by the backend. V6's on-chain timeout functions refund the held entry to the challenger and reopen an unsettled attempt; a timeout is not a player loss. Unreproducible historical records require investigation, not a fabricated win or refund.

Keep D1 point-in-time recovery and restricted log retention enabled. Export audit records to your retention system, restrict database/schema administration, and never enable body logging or provider exception dumps on the signer/relay services. Roll back UI/worker code only to a version compatible with the new immutable schema; never roll back by dropping the settlement records or journals.
